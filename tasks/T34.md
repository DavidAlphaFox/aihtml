# T34 · Jinja 测试基线：fixture 生成器与 harness

- **阶段**：8
- **依赖**：无（可与 T31–T33 并行）
- **状态**：已完成

## 目标

建立 Jinja2 的一致性测试基线。**期望输出由 CPython Jinja2 产生，不由人手写。**

## 交付物

- `tools/gen_jinja_fixtures.py` —— 生成器（开发者用，CI 与测试不依赖 Python）
- `tools/jinja_cases.py` —— 用例源（模板 + context，无期望值）
- `test/jinja_spec/*.json` —— 生成的 fixture，**提交进仓库**
- `test/ai_jinja_test_lib.erl` —— 加载、key 转换、阶段判定
- `test/ai_jinja_spec_tests.erl` —— EUnit generator
- `test/ai_jinja_test_lib_tests.erl` —— 支撑库自测

## 实现要点

### 0. 为什么必须有这一步

[designs/13 §2](../designs/13-jinja-roadmap.md)：Jinja2 没有语言级 spec。
而 [09 §3.2](../designs/09-jinja-syntax.md) 里 `**` 的结合性这类细节，
**人的直觉是错的** —— Jinja2 的 `**` 是左结合，与 Python 相反。
这种坑靠代码审查发现不了，只能靠参照实现实测。

### 1. fixture 格式

```json
{"name": "for/loop-index",
 "template": "{% for x in xs %}{{ loop.index }}{% endfor %}",
 "context": {"xs": [10, 20, 30]},
 "expected": "123",
 "group": "for",
 "stage": 12}
```

错误用例：

```json
{"name": "error/unknown-filter",
 "template": "{{ x|nosuch }}",
 "error": "unknown_filter",
 "stage": 12}
```

已知偏离：

```json
{"name": "deviation/chained-compare",
 "template": "{{ 1 < x < 3 }}",
 "context": {"x": 2},
 "deviation": "J3",
 "error": "chained_comparison",
 "stage": 9}
```

`deviation` 字段存在时，harness 断言**我们的行为**（`error` 或 `expected` 由我们填），
并且不与 CPython 输出比对。生成器对这类用例只记录 CPython 的结果作为注释，供人工核对。

### 2. 用例覆盖清单

按 [09](../designs/09-jinja-syntax.md) 的文法逐条构造，分组与最少用例数：

| 组 | 最少用例 | 内容 |
|---|---|---|
| `lexer` | 30 | 数字/字符串各种字面量、转义序列、相邻字符串拼接 |
| `expr` | 60 | 每个运算符 + 优先级组合 + 结合性 + 短路 |
| `whitespace` | 40 | `-`/`+` × `trim_blocks` × `lstrip_blocks` × `keep_trailing_newline` 的组合矩阵 |
| `if` | 15 | elif 链、嵌套、真值边界 |
| `for` | 40 | loop 全字段、else、解构、内联 filter、recursive、各种可迭代类型 |
| `set` | 20 | 行内/块形式、作用域逃逸规则（[10 §2.4](../designs/10-jinja-semantics.md)）|
| `filters` | 120 | 每个内置 filter 至少 2 条（正常 + 边界） |
| `tests` | 40 | 每个内置 test 至少 1 条 |
| `escape` | 30 | safe 传播分类表（[10 §4.2](../designs/10-jinja-semantics.md)）每条 |
| `inherit` | 30 | extends/block/super、多级、scoped、required |
| `macro` | 25 | 参数默认值、varargs/kwargs、call/caller、import/from |
| `include` | 15 | ignore missing、with/without context |
| `error` | 40 | [11 §9](../designs/11-jinja-codegen.md) 的每个 Reason 至少 1 条 |

合计约 **505** 条。inventory 断言真跑（对齐 mustache 侧 136 条的做法）。

### 3. key 转换

fixture 的 context 是 JSON，key 是字符串；本实现的 map key 是 atom
（[10 §1](../designs/10-jinja-semantics.md)）。harness 递归转换，
与 `ai_mustache_test_lib` 的做法一致，**可直接复用那份实现**。

JSON `null` → atom `null`。

### 4. 阶段判定

`stage` 字段标注该用例在哪个阶段应当点亮。当前实现阶段之后的用例 **skip 而非 fail**，
用 EUnit 的 `{Name, fun() -> ... end}` + `?_test(?debugFmt)` 或直接返回
`{Name, ?_assert(true)}` 并计入 pending 计数。与 mustache 侧一致。

`ai_jinja_test_lib:current_stage/0` 从一个常量读，随实现推进手动上调。

### 5. 生成器要求

- 固定 Jinja2 版本（写进脚本头部与 README），换版本要重新生成并 review diff。
- `Environment` 的配置必须与本实现的默认值一致：`autoescape=True`,
  `trim_blocks=True`, `lstrip_blocks=True`, `keep_trailing_newline=False`。
  **这一点极易出错** —— 参照实现的默认值与我们的默认值不同（[10 §9](../designs/10-jinja-semantics.md) J8）。
- 生成的 JSON 排序稳定、缩进固定，保证重新生成时 diff 最小。
- 脚本本身要能报告「哪些用例 CPython 渲染失败」，那通常是用例写错了。

## 验收标准

- [ ] `rebar3 eunit` 退出码 0，未实现阶段的用例 pending 而非 fail
- [ ] inventory 断言真跑：各组用例数与 §2 的清单一致，总数断言存在
- [ ] 元测试：[10 §9](../designs/10-jinja-semantics.md) 的 J1–J13 每一条至少有一个 `deviation` fixture
- [ ] 元测试：[11 §9](../designs/11-jinja-codegen.md) 的每个 error Reason 至少有一个 fixture

- [ ] 生成器连跑两次产出字节相同的 JSON
- [ ] `ai_jinja_test_lib` 自身的测试全部真跑
