# T25 · 形态 c：编译入口与 staleness 兜底（-mustache_template）

- **阶段**：5
- **依赖**：[T22](T22.md)、[T13](T13.md)
- **状态**：已完成

## 目标

在 parse_transform 的 pass 1/3 中实现 `-mustache_template({Name, Path})`：编译期读取模板文件、编译成本模块内的 `Name/1` 与 `Name_iolist/1` 函数并自动 export；同时与 [T17](T17.md) 交叉确认 plugin 侧的 staleness 兜底行为，并在无 plugin 时给出可用的替代路径。

## 交付物

- `ai_mustache_transform` 的 `collect/2` 中 `-mustache_template` 分支
- `ai_mustache_transform` 的 `inject/2` —— 生成函数 forms 与 export 追加
- `src/ai_mustache_path.erl` —— 模板路径解析（transform 与 plugin 共用，见 §4）
- `test/fixtures/transform_all_three/` —— 同时用到三种形态的示例项目（[07 阶段 5 验收](../designs/07-roadmap.md)）
- `test/ai_mustache_template_tests.erl` —— 形态 c 的用例
- README 中形态 c 的说明与 plugin-recommended 标注

## 实现要点

### 1. attribute 形态与收集

[06 §4](../designs/06-parse-transform.md)：

```erlang
-mustache_template({index, "views/index.mustache"}).
%% 生成 index/1 和 index_iolist/1，并自动 export
```

支持的形态：

| 写法 | 语义 |
|---|---|
| `-mustache_template({index, "views/index.mustache"}).` | 生成 `index/1` 与 `index_iolist/1` |
| `-mustache_template("views/index.mustache").` | 函数名由文件 basename 推导（`index`），规则与 [T18](T18.md) 的模块命名一致但不加 prefix |
| 其它形态 | 报 `{bad_mustache_template, Term}` |

一个模块可以有多条 `-mustache_template`，全部累积到 `#st.templates`。同一模块内 `Name` 重复 → 报 `{duplicate_template_name, Name}`；`Name` 与用户已定义的 `Name/1` 冲突 → 报 `{template_name_clash, Name, Line}`（在 pass 3 注入前扫描已有函数定义来判定，报错优于静默覆盖）。

### 2. 路径解析

[06 §4](../designs/06-parse-transform.md) 定义的顺序：

> 路径解析顺序：模块所在目录 → `{mustache_opts, {views, ...}}` → 编译选项 `i` 路径。

实现为 `ai_mustache_path:resolve(Path, SearchDirs) -> {ok, AbsPath} | {error, {not_found, TriedDirs}}`：

1. 绝对路径 → 直接用。
2. 相对路径依次在以下目录下试：
   - 当前 `.erl` 所在目录（从 `#st.file` 取 `filename:dirname/1`）；
   - `{mustache_opts, [{views, Dir}]}` 指定的目录（从 `#st.opts` 读，[T22](T22.md) §2 的 `mopt/3`）；
   - 编译选项中所有 `{i, Dir}`；
   - 编译进程的 cwd（兜底，同时在文档里说明不要依赖它）。
3. 全部落空 → `{template_not_found, Path, TriedDirs}`，**错误文案必须列出实际试过的全部目录**（[T22](T22.md) §3），否则用户完全无从下手。

### 3. 编译与函数生成

pass 1 收集时不做 IO；**pass 3 inject 时**才读文件并编译。这样保证 pass 1 的纯校验性质，也避免路径解析失败时做多余工作。

流程：

```
file:read_file(AbsPath)
  → ai_mustache_scanner → ai_mustache_parser → AST
  → ai_mustache_compiler:forms(AST, Opts)
  → 取出其中的函数 forms，改名后注入本模块
```

关键设计问题：**compiler 的 `forms/2` 产出的是一个完整模块**（含 `-module` / `-export` / `render/1` / `render_stack/2` / `partials/0` / `-mustache_source`，见 [04 §4](../designs/04-codegen.md)），而形态 c 需要的是「注入到已有模块里的若干函数」。两种处置：

- **(A) 剥离外壳**：调 `forms/2` 后丢掉 `-module` / `-export` / `-mustache_source`，把 `render/1` 改名为 `Name/1`、`render_iolist/1` 改名为 `Name_iolist/1`，把内部辅助函数（`sec_N/2` / `lam_N/1` / `render_stack/2`）加上唯一前缀避免与用户函数及多条 `-mustache_template` 之间冲突。
- **(B) 给 compiler 加选项**：`forms/2` 接受 `#{shape => module | fragment, fun_prefix => binary()}`，`fragment` 形态直接产出可注入的函数列表且函数名带前缀。

**推荐 (B)** —— 剥离与改名的逻辑放在 compiler 里，两个消费者共享同一份实现，符合[架构不变量 #2](../designs/02-architecture.md)；(A) 会让 transform 里长出一堆对生成代码结构的假设，compiler 一改就断。实现时把这个选择写进 compiler 的接口文档。

无论哪种，必须保证：

- 内部函数名唯一：多条 `-mustache_template` 各自的 `sec_1` 不能撞。前缀方案用 `'-mustache-index-sec-1-'` 这类带连字符的 atom（用户写不出来）。
- 自动 export：pass 3 追加一个 `{attribute, L, export, [{Name, 1}, {NameIolist, 1}]}` form，插在最后一个已有 export 之后 / 第一个函数定义之前。注意 Erlang 要求 `-export` 出现在所有函数定义之前，插错位置会编译失败。
- **partial 的处置**：形态 c 的模板里可以有 `{{> x}}`，它会被编译成 `view_x:render_stack(S, I)` 的跨模块调用（[02 §2.2](../designs/02-architecture.md)）。这要求 `view_x` 由 plugin 编译存在。若项目不用 plugin，这个调用在运行期会 undef。处置：pass 3 检查模板中是否含 partial，若含且 `#st.opts` 中无 plugin 迹象，发 warning `{template_partial_needs_plugin, Name, Partials}`，文案说明需要用 plugin 编译这些 partial。**不报错** —— 用户可能手工编译了 partial 模块。
- 扩展 tag 可用：把 `#st.ext_tags`（[T23](T23.md)）构建成分派表传给 compiler 的 `extensions` 选项。这是 `-mustache_tag` 参与装配的另一个场景。
- `-mustache_template` attribute 在 pass 2 中**不剔除** —— 与形态 a 相反。理由：plugin 的 staleness 兜底（§4）要从**源文件**扫描它，虽然 plugin 读的是 `.erl` 源文本而非 beam attribute，但保留它在 beam 里对诊断（`Mod:module_info(attributes)` 能看出这个模块依赖哪些模板）有价值，也让 `ai_mustache_dev` 将来可以复用。**这一点要在实现中明确注释**，否则容易被当作遗漏而「顺手」删掉。

### 4. staleness 兜底 —— 与 T17 交叉

[06 §4.1](../designs/06-parse-transform.md) 指出的已知成本：

> 改 `views/index.mustache` 不会触发 `my_views.erl` 重编 —— parse_transform 无法向 rebar3 注册额外的文件依赖（只有 `-include` 会被跟踪）。

[05 §6](../designs/05-rebar3-plugin.md) 的兜底方案在 **plugin 侧**实现，已写进 [T17](T17.md) §6：扫描 `-mustache_template` 建反向依赖表，模板 hash 变化时 `touch` 对应 `.erl`。

本任务对这条交叉的责任：

1. **共享路径解析** —— plugin 与 transform 必须用**同一套**解析顺序，否则 plugin touch 的文件与 transform 实际读的文件不是同一个，兜底就失效了。做法是把 `ai_mustache_path:resolve/2` 抽成独立模块，plugin 侧（[T17](T17.md)）直接调它。若 plugin 因加载域问题拿不到这个模块，则把它复制到 plugin 子项目并加一条「两份必须同步」的测试（用同一张用例表跑两边）。
2. **attribute 形态对齐** —— plugin 的静态扫描要能认出本任务支持的**全部** attribute 形态（§1 的两种）。测试中要有一条断言：`ai_mustache_path` / plugin 扫描器解析出的 `{Name, Path}` 与 transform 收集到的 `#st.templates` 一致。
3. **无 plugin 时的替代路径** —— [06 §4](../designs/06-parse-transform.md) 说保留形态 c 的价值在于「不依赖 plugin 也能用（比如纯 erlang.mk 或手写 Makefile 的项目）」。这些场景下没有兜底，改模板不会重编。处置：
   - README 中把形态 c 明确标注为 **plugin-recommended**（[07 风险表](../designs/07-roadmap.md)）；
   - 提供一个 `-include` 的可选变通：文档中说明用户可以 `-include("views/index.mustache.hrl")` 之类的空 hrl 与模板同步 touch 来借用 rebar3 的 include 依赖跟踪 —— 这个变通丑但有效，写在 README 的 FAQ 里而不是强制实现。

### 5. 无 transform 时的行为

[06 §6](../designs/06-parse-transform.md) 的对比表：形态 c 在「无 transform 时」是**不生成函数，编译报错**（调用方引用 `Name/1` 时 undef）。

这与形态 a（丢失校验）、形态 b（降级为运行期）不同，是三形态中唯一的硬失败。要在测试中固定这个行为，并在 README 中明确：**形态 c 必须配 `-compile({parse_transform, ai_mustache_transform})`，否则不工作。**

由于 `-mustache_template` 是未知 attribute，Erlang 编译器本身不会报错（未知 attribute 是合法的），所以用户漏加 parse_transform 时得到的错误是「函数 `index/1` 未定义」，指向调用点而非 attribute。可以在 README 的常见错误一节里写明这个症状。

## 验收标准

- [ ] `-mustache_template({index, "views/index.mustache"}).` 生成 `index/1` 与 `index_iolist/1` 并自动 export
- [ ] `-mustache_template("views/index.mustache").` 能从 basename 推导出函数名 `index`
- [ ] 其它形态报 `{bad_mustache_template, Term}` 并给出正确写法
- [ ] 同一模块内多条 `-mustache_template` 各自正常工作，内部辅助函数名互不冲突
- [ ] `Name` 重复、`Name` 与用户已有 `Name/1` 冲突时各报独立可读错误
- [ ] 路径解析按「模块所在目录 → `mustache_opts` 的 `views` → 编译选项 `i`」的顺序，每一级各有一条测试
- [ ] 模板找不到时报错，文案列出实际试过的**全部**目录
- [ ] 追加的 `-export` 位置正确（在所有函数定义之前），编译通过
- [ ] 模板内的编译错误报出的 File 是 `.mustache` 路径、Line 是模板行号（[T22](T22.md) §3）
- [ ] 模板中含 partial 时发出 `template_partial_needs_plugin` warning 但不报错；partial 模块存在时渲染正确
- [ ] 同模块内 `-mustache_tag` 声明的扩展在形态 c 的模板中可用
- [ ] `-mustache_template` attribute 在生成的 beam 的 `module_info(attributes)` 中**保留**（与形态 a 相反，代码中有注释说明理由）
- [ ] `ai_mustache_path:resolve/2` 为 transform 与 plugin 共用；若有两份拷贝，有同表驱动的一致性测试
- [ ] plugin 静态扫描解析出的 `{Name, Path}` 与 transform 收集到的 `#st.templates` 一致（对照测试）
- [ ] 改模板后 `rebar3 compile` 能重编该模块（与 [T17](T17.md) §6 联调，端到端 case 在 [T20](T20.md)）
- [ ] 去掉 `-compile({parse_transform, ...})` 后编译失败，且失败信息可理解；此行为有测试固定
- [ ] `test/fixtures/transform_all_three/` 同时使用三种形态，编译并渲染正确（[07 阶段 5 验收](../designs/07-roadmap.md)）
- [ ] README 中形态 c 标注为 plugin-recommended，并写明漏加 parse_transform 时的症状
