# T09 · AST 后处理三 pass

- **阶段**：2
- **依赖**：[T08](T08.md)
- **状态**：已完成

## 目标

实现 `merge_text/1`、`drop_empty/1`、`resolve_partials/2` 三个 AST 变换 pass，一次性修掉 [P1](../designs/01-current-state.md)（后处理 O(n²)）、[P2](../designs/01-current-state.md)（合并不下钻 `{{+}}`）、[P3](../designs/01-current-state.md)（空 section 消除只处理顶层且含死代码）。

## 交付物

- `src/ai_mustache_ast.erl` —— 三个 pass 与统一的 `postprocess/2` 入口

> [designs/02-architecture.md §3](../designs/02-architecture.md) 的目录结构里没有列这个模块（后处理隐含在 parser 里）。**独立成模块**是有意的：三个 pass 与语法分析没有耦合、需要各自单测（[T10](T10.md)）、且 `resolve_partials/2` 的模块名归一化要与 plugin 共用。若坚持按设计文档的模块清单走，则三个函数放进 `ai_mustache_parser` 并单独导出，其余要点不变。

## 实现要点

### 1. 接口

```erlang
-module(ai_mustache_ast).
-include("ai_mustache.hrl").
-export([postprocess/2, merge_text/1, drop_empty/1, resolve_partials/2]).

-spec merge_text([ai_mustache_node()]) -> [ai_mustache_node()].
-spec drop_empty([ai_mustache_node()]) -> [ai_mustache_node()].
-spec resolve_partials([ai_mustache_node()], ai_mustache_opts()) ->
        {ok, [ai_mustache_node()], Deps :: [module()]} | ai_mustache_error().

-spec postprocess([ai_mustache_node()], ai_mustache_opts()) ->
        {ok, [ai_mustache_node()], Deps :: [module()]} | ai_mustache_error().
```

`postprocess/2` 按 `merge_text → drop_empty → resolve_partials` 顺序串联。顺序不可换：`drop_empty` 依赖 `merge_text` 之后的结果（合并后才能判断 body 是否只剩空白），`resolve_partials` 放最后是因为它可能返回错误、放前面会浪费前两 pass 的工作。

三个 pass 分别导出，便于 [T10](T10.md) 单独测。

### 2. 通用的「下钻」原则

**三个 pass 都必须递归进入所有含 body 的节点**：

```erlang
{section,  Loc, Keys, Body}
{inverted, Loc, Keys, Body}
{has,      Loc, Keys, Body, Pos}
{ext,      Loc, C,    Keys, Body}
```

这直接修掉 [P2](../designs/01-current-state.md)：旧 `merge_continuous_binary/1` 只对 `{section, ...}` 递归，`{has, ...}` 内部的连续静态文本不合并，导致 `{{+x}}` 块内在运行期反复 binary append。写一个统一的 `map_body/2` 高阶函数，让三个 pass 复用同一套下钻逻辑，避免漏掉某个节点类型：

```erlang
map_body(F, {section, L, K, B})   -> {section, L, K, F(B)};
map_body(F, {inverted, L, K, B})  -> {inverted, L, K, F(B)};
map_body(F, {has, L, K, B, P})    -> {has, L, K, F(B), P};
map_body(F, {ext, L, C, K, B})    -> {ext, L, C, K, F(B)};
map_body(_, N)                    -> N.
```

新增 AST 节点类型时只需改这一处。

### 3. `merge_text/1`

合并相邻的 `{text, Loc, Bin}`。

- 用 `[Node | Acc]` + 末尾 `lists:reverse/1`，**禁止 `Acc ++ [I]`** —— 这是 [P1](../designs/01-current-state.md) 的根因，旧实现在 `ai_mustache_parser.erl:328,338,341,363,366` 五处都是这个写法。
- 待合并的文本片段先收进一个反序列表 `Pending`，flush 时用 `iolist_to_binary(lists:reverse(Pending))` 一次成型，而不是 `lists:foldl(fun(B, A) -> <<A/binary, B/binary>> end, <<>>, L)`（旧实现的写法，O(n²) 拷贝）。
- 合并后节点的 `loc()` **取第一个片段的 loc**，保持「指向起始位置」的一致约定。
- 合并结果为 `<<>>` 时整个节点丢弃（scanner 已保证不产空 text，但合并逻辑要自洽）。

### 4. `drop_empty/1`

移除 body 为空的节点，**但必须区分节点类型**：

| 节点 | body 为 `[]` 时 |
|---|---|
| `{section, ...}` | **丢弃** —— `{{#x}}{{/x}}` 无输出且无副作用 |
| `{inverted, ...}` | **保留** —— 见下方警告 |
| `{has, ...}` | **丢弃** —— 纯条件渲染，无 body 即无输出 |
| `{ext, ...}` | **保留** —— 扩展语义未知，行内扩展本来就 body 为空 |

> **`{{#x}}{{/x}}` 丢弃是有副作用风险的**：当 `x` 是 `fun/2` lambda 时，标准语义要求调 `F(<<>>, Frame)` 并**输出其返回值**。所以 `drop_empty/1` 对 `{section, ...}` 的丢弃条件应收紧为「body 为空 **且** 无法在编译期证明该 key 不是函数」—— 而编译期证明不了。**结论：`{section, ...}` 的空 body 也保留，只在 [T13](T13.md) 的代码生成里把 body 函数生成为 `_body(_S, _I) -> []`。**设计文档 [04 §2](../designs/04-codegen.md) 写的是「移除空 body 的 section（保留 inverted）」，实现时须按此处更严格的判断收敛，并在 `drop_empty/1` 的模块注释中记录这一偏差理由。
>
> `{{^x}}{{/x}}` 保留的理由文档已给出：inverted 的空 body 仍有语义（它本身不输出，但存在与否不影响结果 —— 保留是为了不改变错误诊断与后续 pass 的形状，且 inverted 永不调用 lambda）。

`{has, ...}` 可以安全丢弃：`{{+x}}` 只做布尔判定，`fun/1` 形态的返回值不参与输出（[designs/03-semantics.md §4](../designs/03-semantics.md)）。但若该 `fun/1` 有副作用，丢弃会改变行为 —— 在模块注释中标注为「有意的编译期优化，lambda 副作用不保证」。

**同时修掉 P3 的两个具体问题**：

1. 旧 `remove_empty_section/1` **只遍历顶层不递归**，新实现必须下钻（走 `map_body/2`）。
2. 旧代码中的 `[<<>>]` 分支是**死代码** —— `?ADD` 宏保证空 binary 不入 IR，且 IR 里是 `{binary, B}` 而非裸 binary。新实现不得复制这个分支。

### 5. `resolve_partials/2`

把 `{partial, Loc, Name :: binary(), Indent}` 中的 `Name` 解析为目标模块名，并汇总依赖列表。

**模块名归一化**（与 [designs/05-rebar3-plugin.md §4](../designs/05-rebar3-plugin.md) 完全一致，实现必须共用同一函数，plugin 侧扫描目录时也调它）：

```
去掉 views/ 前缀与 .mustache 后缀 → 路径分隔符 `/` 与 `-` 归一为 `_` → 加 prefix（默认 <<"view_">>）
```

- `<<"index">>`          → `view_index`
- `<<"shared/item">>`    → `view_shared_item`
- `<<"layout/default">>` → `view_layout_default`

节点改写为 `{partial, Loc, Mod :: module(), Indent}`（第三字段类型从 `binary()` 变为 `module()`）。**这个类型变化要在 `include/ai_mustache.hrl`（[T06](T06.md)）中体现** —— 建议 `Name :: binary() | module()`，并在类型注释里写明「`resolve_partials/2` 之前是 binary，之后是 module」。

**存在性校验**：`opts` 中给了 `views` 时，检查 `filename:join(Views, <<Name/binary, Suffix/binary>>)` 是否存在，不存在报 `{partial_not_found, Name}`。未给 `views`（如 parse_transform 的内联场景）时跳过校验 —— 但内联模板根本不允许 partial，那由 [T14](T14.md) 单独报错。

**依赖列表**：去重后的 `[module()]`，按名字排序保证生成代码稳定（同一模板每次生成的 `.erl` 必须字节一致，否则增量编译的 hash 判断会抖动）。递归下钻收集，`{{#x}}{{> p}}{{/x}}` 里的 `p` 也要进依赖列表。

**不做循环检测**：partial 编译成跨模块调用，循环引用天然合法（[designs/02-architecture.md §2.2](../designs/02-architecture.md)）。`{partial_cycle_depth, [module()]}` 这个错误码保留给 parse_transform 的内联展开路径（[T14](T14.md)），本 pass 不使用。

### 6. 稳定性要求

三个 pass 都是纯函数，无进程、无 ets、无 `erlang:put/2`。同一输入必须产出逐字节相同的输出（`term_to_binary/1` 可比较）—— 这是增量编译 hash 可靠的前提。

## 验收标准

- [ ] `merge_text/1` 递归下钻到 `section` / `inverted` / `has` / `ext` 四种 body（P2 修复），有针对 `{{+x}}` 内嵌连续文本的测试
- [ ] `merge_text/1` 不产生 `Acc ++ [X]`，全文件 grep 不到该写法（P1 修复）
- [ ] `merge_text/1` 用 `iolist_to_binary/1` 一次成型，不做二元 `<<A/binary, B/binary>>` 折叠
- [ ] `drop_empty/1` 递归下钻，不含 `[<<>>]` 死代码分支（P3 修复）
- [ ] `drop_empty/1` 保留空 body 的 `inverted` 与 `section`，丢弃空 body 的 `has`，模块注释记录理由
- [ ] `resolve_partials/2` 正确处理 `shared/item`、`layout/default`、`layout.default` 三种路径形态
- [ ] `resolve_partials/2` 返回的 Deps 已去重并排序
- [ ] 嵌套在 section 内的 partial 也进入 Deps
- [ ] `views` 存在时缺失 partial 报 `{partial_not_found, Name}`，含 `..` 的路径报错
- [ ] `postprocess/2` 幂等：`postprocess(postprocess(AST))` 与 `postprocess(AST)` 结果相同
- [ ] 模块名归一化函数与 plugin 侧共用同一实现（xref 可见调用关系，无重复定义）
- [ ] 同一模板两次 postprocess 的 `term_to_binary/1` 结果一致
