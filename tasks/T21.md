# T21 · ai_mustache_ext behaviour

- **阶段**：5
- **依赖**：[T06](T06.md)
- **状态**：已完成

## 目标

定义 `ai_mustache_ext` behaviour，让用户能注册自定义 marker 并在编译期把扩展 tag 编译成 Erlang abstract expression；同时在 compiler 中接入 `{ext, ...}` 节点的编译分派与 marker 冲突检测。

## 交付物

- `src/ai_mustache_ext.erl` —— behaviour 定义（`markers/0` · `compile_tag/4` · 可选 `block_markers/0`）
- `src/ai_mustache_ext_reg.erl` —— 扩展模块列表的校验、marker → 模块的分派表构建、冲突检测
- `ai_mustache_compiler` 中 `{ext, Loc, Marker, Keys, Body}` 节点的编译分支
- `test/ai_mustache_ext_tests.erl` 中扩展 behaviour 的 EUnit 用例（阶段 1 已建骨架，本任务点亮）
- `test/fixtures/exts/my_i18n.erl` —— 示例扩展模块，作为文档与测试的双重载体

## 实现要点

### 1. behaviour 定义

严格照 [06 §2.1](../designs/06-parse-transform.md)：

```erlang
-module(ai_mustache_ext).

%% 本扩展模块接管哪些 marker 字符
-callback markers() -> [char()].

%% 编译期把一个扩展 tag 编译成 Erlang abstract expression
%%   Marker : 触发的字符，如 $@
%%   Keys   : tag 中的点分路径，如 [greeting, title]
%%   Body   : 块级扩展的 body 已编译 forms；行内扩展为 []
%%   Opts   : 编译选项，含 module / source / 用户自定义配置
%% 返回的表达式求值结果必须是 iodata()
-callback compile_tag(Marker :: char(), Keys :: [atom()],
                      Body :: [erl_parse:abstract_expr()],
                      Opts :: map()) -> erl_parse:abstract_expr().

%% 可选：声明该 marker 是块级（需要 {{/x}} 闭合）还是行内
-callback block_markers() -> [char()].
-optional_callbacks([block_markers/0]).
```

模块本身除了 callback 声明外，还导出几个给 compiler 与 [T23](T23.md) 共用的工具函数（放在同一模块或 `ai_mustache_ext_reg`，二选一并保持一致）：

- `builtin_markers() -> [char()]` —— 返回内置已占用集合，见 §3
- `is_block(Module, Marker) -> boolean()` —— 若模块未导出 `block_markers/0` 则返回 `false`（行内）
- `registry([module()]) -> {ok, #{char() => module()}} | {error, Reason}` —— 构建分派表并做冲突检测

### 2. `Opts` 的内容契约

`compile_tag/4` 的第四个参数是 compiler 的 opts map（[04 §3](../designs/04-codegen.md)），扩展作者会依赖它，因此必须把可见字段固定成契约并写进文档：

| key | 说明 |
|---|---|
| `module` | 正在生成的模块名 |
| `source` | 模板源路径（binary），用于扩展自己产出诊断 |
| `loc` | 当前 ext tag 的 `{Line, Col}`，本任务在 compiler 分派时注入 |
| `stack_var` | 栈变量的 abstract 变量名，当前固定为 `'S'` |
| `indent_var` | 缩进变量的 abstract 变量名，当前固定为 `'I'` |
| `line_map` | 是否用模板行号 |
| `ext_opts` | 用户自定义配置，来自 `{mustache_opts, [{ext_opts, #{Module => term()}}]}` |

关键点：**`stack_var` 必须作为契约暴露，而不是让扩展作者硬编码 `{var, L, 'S'}`。**[06 §2.2](../designs/06-parse-transform.md) 的示例里直接写了 `{var, L, 'S'}`，那是示例的简写；生成代码里栈变量名可能因为 section body 拆函数而变化，硬编码会在嵌套场景下产出引用未绑定变量的代码。实现时在文档与示例中都改成从 `Opts` 取。

### 3. 内置 marker 与冲突检测

[06 §2.4](../designs/06-parse-transform.md) 明确：

> 内置已占用：`# ^ / > ! = & { } + - *`。扩展只能注册这些之外的字符。

冲突检测三类，全部报**编译错误**：

1. **扩展 marker 与内置冲突** → `{marker_reserved, Marker, Module}`
2. **两个扩展模块注册同一 marker** → `{marker_conflict, Marker, [ModA, ModB]}`，错误信息必须列出全部冲突模块
3. **扩展模块不合法** → 三个子类：
   - 模块无法加载（`code:ensure_loaded/1` 失败）→ `{ext_module_not_found, Module}`
   - 未声明 `-behaviour(ai_mustache_ext)` → `{not_an_ext_module, Module}`（读 `Module:module_info(attributes)` 的 `behaviour` / `behavior` 两种拼写）
   - 未导出 `markers/0` 或 `compile_tag/4` → `{ext_missing_callback, Module, {F, A}}`

其它需要拦住的输入：

- `markers/0` 返回非 char 或返回空列表 → 报错（注册了却不接管任何字符，多半是笔误）
- marker 是空白字符、`}`、`{` 或非 ASCII 可打印字符 → 报错（scanner 无法可靠切分）
- `block_markers/0` 返回的字符不在 `markers/0` 中 → 报错

分派表构建是确定性的：输入列表先 `lists:usort/1`，冲突报告按 marker 与模块名排序，保证同一配置的错误输出可复现。

### 4. compiler 中 `{ext, ...}` 的编译分派

AST 节点是 `{ext, loc(), Marker :: char(), keys(), [node()]}`（[04 §1](../designs/04-codegen.md)）。compiler 的编译流程：

1. 从 `Opts` 的 `extensions` 构建（或接收已构建好的）分派表 `#{char() => module()}`。
2. 遇到 `{ext, Loc, Marker, Keys, Body}`：
   - 查表；未命中 → `{error, {File, Line, {unknown_marker, Marker}}}`（[04 §7](../designs/04-codegen.md) 已定义此 Reason）
   - 命中 `Mod`，先**递归编译 `Body`** 得到 `[abstract_expr()]`（行内扩展时 `Body = []`）
   - 调 `Mod:compile_tag(Marker, Keys, BodyForms, Opts#{loc => Loc})`
   - 把返回的表达式原地嵌入外层 iolist
3. **扩展返回值必须校验**：
   - 返回的不是合法 abstract expression（用 `erl_syntax:is_tree/1` + 尝试 `erl_prettypr:format/1`，或直接 `erl_lint` 一遍包装后的 form）→ 报 `{ext_bad_form, Module, Marker}`，附上扩展模块名。**不要让坏 form 一路漏到 `compile:forms` 才炸**，那时的错误信息完全指不回扩展模块。
   - 扩展在 `compile_tag/4` 中抛异常 → 捕获并包装为 `{ext_crashed, Module, Marker, Class, Reason}`，附 stacktrace 摘要。扩展是用户代码，崩了不能让整个 plugin 栈爆开。
4. **不做转义**：扩展的返回值语义是 iodata，直接进 iolist。要转义是扩展自己的事（这与 `{{*f}}` lambda 的约定一致，见 [03 §5](../designs/03-semantics.md)）。这一点必须在 behaviour 文档中显著标注 —— 扩展默认不转义意味着扩展作者要对 XSS 负责。
5. 块级判定与 scanner/parser 的配合：parser 需要知道某个 marker 是块级（要找 `{{/x}}` 闭合）还是行内。这个信息在 parse 阶段就要用到，因此**分派表必须在 parse 之前构建并传给 parser**，不能等到 compile 阶段。这是一个跨阶段的接口约束，[T06](T06.md) / [T08](T08.md) 的 AST 与 parser 设计里要留出 `#{char() => block | inline}` 这个入参。

### 5. 示例扩展模块

照 [06 §2.2](../designs/06-parse-transform.md) 实现 `my_i18n`，但修正示例中的硬编码问题：

```erlang
-module(my_i18n).
-behaviour(ai_mustache_ext).
-export([markers/0, compile_tag/4]).

markers() -> [$@].

%% {{@ hello}}  →  my_i18n_rt:t(hello, ai_mustache_rt:lookup([locale], S))
compile_tag($@, [Key], [], Opts) ->
    L = line_of(Opts),
    SVar = {var, L, maps:get(stack_var, Opts, 'S')},
    {call, L, {remote, L, {atom, L, my_i18n_rt}, {atom, L, t}},
     [{atom, L, Key},
      {call, L, {remote, L, {atom, L, ai_mustache_rt}, {atom, L, lookup}},
       [{cons, L, {atom, L, locale}, {nil, L}}, SVar]}]}.
```

这个模块同时是 [T23](T23.md) 与 [T20](T20.md) 的 fixture，放 `test/fixtures/exts/` 下并在文档中引用。

### 6. 装配 vs 声明的边界

必须在 behaviour 的模块文档中写清 [06 §2.3](../designs/06-parse-transform.md) 的职责切分：

| 机制 | 职责 |
|---|---|
| `-mustache_tag` + parse_transform | **声明与校验**（[T23](T23.md)），parse_transform 作用域是单模块，管不到模板的编译 |
| `{mustache_opts, [{extensions, [my_i18n]}]}` | **实际装配**，告诉 compiler 编译模板时启用哪些扩展 |

本任务实现的是**装配侧**：`extensions` 列表 → 分派表 → compiler 分派。声明侧在 [T23](T23.md)。二者共用同一个 `ai_mustache_ext_reg` 的校验函数，保证「parse_transform 编译期报的错」与「plugin 装配时报的错」文案一致。

## 验收标准

- [ ] `ai_mustache_ext` 定义了 `markers/0` · `compile_tag/4` 两个必选 callback 与可选 `block_markers/0`
- [ ] `builtin_markers/0` 返回的集合恰好是 `# ^ / > ! = & { } + - *` 共 12 个字符
- [ ] 扩展注册内置 marker（如 `$#`）时报 `marker_reserved` 错误
- [ ] 两个扩展模块注册同一 marker 时报错，错误信息列出**全部**冲突模块
- [ ] 扩展模块不存在 / 未声明 behaviour / 缺少 callback 三种情况各有独立的可读错误
- [ ] `markers/0` 返回空列表、返回非法字符（空白、`{`、`}`）时报错
- [ ] `block_markers/0` 返回不在 `markers/0` 中的字符时报错
- [ ] `{{@ hello}}` 经 `my_i18n` 编译后生成正确的 `my_i18n_rt:t/2` 调用，渲染结果正确
- [ ] 块级扩展 `{{@x}}...{{/x}}` 的 body 被递归编译并作为 `Body` 传给 `compile_tag/4`
- [ ] `compile_tag/4` 返回非法 form 时报 `ext_bad_form` 并指出扩展模块名，而不是在 `compile:forms` 阶段崩溃
- [ ] `compile_tag/4` 抛异常时被捕获并包装为可读错误，不影响其它模板的编译
- [ ] 扩展的返回值不被 HTML 转义，且此约定在模块文档中显著标注
- [ ] 扩展表达式中从 `Opts` 取 `stack_var`，在嵌套 section body 内使用扩展 tag 时生成的代码引用的是正确的栈变量
