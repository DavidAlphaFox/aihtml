# T52 · rebar3 jinja provider 与双引擎共存

- **阶段**：13
- **依赖**：[T51](T51.md) · [T49](T49.md)

## 目标

注册 `rebar3 jinja` provider，落地 `jinja_opts`，并解决两个引擎共存带来的三个跨引擎问题。

## 交付物

- `rebar3_aihtml/src/rebar3_aihtml_jinja.erl`
- `rebar3_aihtml/src/rebar3_aihtml.erl` —— 注册链增加新 provider
- `rebar3_aihtml/src/rebar3_aihtml_check.erl` —— 跨引擎重名 + extends 环检测
- `test/rebar3_aihtml_jinja_SUITE.erl`
- `test/fixtures/jinja_project/` · `test/fixtures/dual_engine/`

## 实现要点

### 1. provider

```erlang
init(State) ->
    P = providers:create([{name, jinja}, {module, ?MODULE}, {namespace, default},
                          {bare, true}, {deps, [app_discovery, install_deps]},
                          {example, "rebar3 jinja"},
                          {opts, [{force, $f, "force", boolean, "..."}]},
                          {short_desc, "Compile Jinja2 templates to Erlang modules"},
                          ...]),
    {ok, rebar_state:add_provider(State, P)}.

do(State) -> rebar3_aihtml_prv:run(State, ai_jinja_engine, Force).
```

`rebar3_aihtml:init/1` 的 foldl 列表加入本模块。

### 2. `jinja_opts`

[12 §1.3](../designs/12-jinja-toolchain.md)。键：
`views suffix out_dir prefix escape trim_blocks lstrip_blocks
keep_trailing_newline strict_undefined extensions line_map warnings_as_errors`。

默认：`views` = `"views"`，`suffix` = `".j2"`，`prefix` = `"j2_"`，
`escape` / `trim_blocks` / `lstrip_blocks` = `true`，
`keep_trailing_newline` / `strict_undefined` = `false`。

### 3. 三个跨引擎问题

#### 3.1 孤儿清理（[T51](T51.md) 已处理 banner，这里验证）

同一 out_dir 下两个引擎的产物，反复 `rebar3 compile` 文件数必须稳定。
**这是必须有的回归测试**，且要跑至少三轮。

#### 3.2 全项目重名检测

两个引擎的产物要进**同一张表**（[12 §1.5](../designs/12-jinja-toolchain.md)）。
做法：冲突表存进 `rebar_state`（`rebar_state:set(State, {aihtml, modules}, Table)`），
第二个 provider 读取并追加。

第二个 provider 没跑时表里只有一半 —— 这是正常的（用户可能只用一个引擎），
不报错。

`view_x.mustache` 与 `view_x.j2`（前缀配成一样时）必须被检出冲突。

#### 3.3 extends 环检测

单模板编译看不出互相继承（[T48](T48.md) §6）。plugin 有全量模板视图，
在 `validate/1` 阶段构建 extends 图并查环，报
`{extends_cycle, [Mod]}`，错误里按环的顺序列出模板路径。

同时构建「宏导出表」供 [T49](T49.md) 的 `{macro_not_found, ...}` 检查使用：
扫描每个模板的 `{% macro %}` 名字，传给 `Engine:forms/2` 的 opts。

### 4. 反向依赖与 parse_transform

`-jinja_template` 的扫描走 `ai_html_path:scan/2`（[T32](T32.md)），
属性名传 `jinja_template`。模板 hash 变了就 touch 对应 `.erl`。

两个引擎各扫各的属性，互不干扰。

### 5. 配置示例

```erlang
{provider_hooks, [{pre, [{compile, mustache}, {compile, jinja}]}]}.
```

顺序无关（有了 §3.1 的 banner 隔离）。**要有一条用例把顺序反过来跑**，
证明确实无关。

## 验收标准

- [ ] `rebar3 jinja` 可独立运行；`rebar3 compile` 通过 hook 触发
- [ ] `jinja_opts` 全部键生效，默认值与 [12 §1.3](../designs/12-jinja-toolchain.md) 一致
- [ ] 未知键警告指明是 jinja 配置
- [ ] **双引擎回归**：同一 out_dir，`rebar3 compile` 连跑三次，文件数与内容稳定
- [ ] **顺序无关**：hook 顺序反过来，结果相同
- [ ] 跨引擎重名被检出（前缀配成相同的用例）
- [ ] extends 环被检出，错误按环顺序列出模板路径
- [ ] 宏导出表传给 compiler，`{macro_not_found, ...}` 在 plugin 路径下生效
- [ ] `-jinja_template` 的反向依赖 touch 生效（改模板后 `.erl` 被重编）
- [ ] 增量：改被 include 的模板不重编 includer 的父模板（[T48](T48.md) 的验收在此端到端复现）
- [ ] `test/fixtures/dual_engine/` 端到端跑通
