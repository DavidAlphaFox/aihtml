# T39 · ai_jinja_parser —— 语句结构

- **依赖**：[T36](T36.md) · [T38](T38.md)
- **状态**：已完成

## 目标

把 scanner 的 token 流组装成块结构的 `jinja_node()` AST，完成全部配对与嵌套校验。

## 交付物

- `src/ai_jinja_parser.erl`
- `test/ai_jinja_parser_tests.erl`

## 实现要点

### 1. 接口

```erlang
-spec parse(unicode:chardata(), map()) ->
        {ok, [jinja_node()]} | ai_html_error(ai_jinja_reason()).
```

内部 `scan → 组装`。与 `ai_mustache_parser:parse/2` 同形，
因此可直接作为 `ai_html_engine:parse/2` 的实现。

### 2. 语句清单

第一档与第二档全部实现（[09 §4.1/§4.2](../designs/09-jinja-syntax.md)）：

```
if / elif / else / endif
for [k, v] in E [if C] [recursive] / else / endfor
set NAME = E          set NAME ... endset
with a = E, ... endwith
filter F ... endfilter
raw ... endraw                      (scanner 已处理，parser 只见 raw token)
include "p" [ignore missing] [with|without context]
do E
extends "p"
block NAME [scoped] [required] ... endblock [NAME]
macro NAME(params) ... endmacro
call [(params)] EXPR ... endcall
import "p" as NAME [with|without context]
from "p" import a[, b as c] [with|without context]
```

第三档（`autoescape` / `trans` / `debug` / `break` / `continue`）遇到即报
`{unknown_statement, Kw, Loc}`，错误文案要说明「本实现不支持，见 docs/jinja.md」。

### 3. 块栈与配对校验

维护 `[{Kind, Loc, Name}]`。八类诊断（[09 §4.4](../designs/09-jinja-syntax.md)）：

| 情况 | Reason |
|---|---|
| `{% endblock name %}` 名字不符 | `{block_name_mismatch, Open, Close}` |
| 闭合与栈顶 Kind 不符 | `{mismatched_end, Expected, Got}` |
| 文件结束时栈非空 | `{unclosed_block, Kind, OpenLoc}` |
| `elif`/`else` 栈顶不是 if/for | `{orphan_clause, Kind}` |
| `for` 的 `else` 出现两次 | `{orphan_clause, else}` |
| 同模板重复 `{% block name %}` | `{duplicate_block, Name, FirstLoc}` |
| 未知语句关键字 | `{unknown_statement, Kw}` |
| 语句参数解析失败 | 透传 `ai_jinja_expr` 的错误 |

**`{% extends %}` 不在顶层首位只报 warning**，不报错 —— Jinja2 允许它出现在任意位置
（只有第一个生效），当成错误会拒掉合法模板。

`{% extends %}` 存在时，对同层的非 `block`/`set`/`macro`/`import`/`from` 节点
发 warning「该内容不会被输出」（[11 §5.1](../designs/11-jinja-codegen.md)）。

### 4. `if` 的分支表示

扁平 `[{Cond, Body}]` + `Else`，**不是**嵌套 if/else（[09 §5.2](../designs/09-jinja-syntax.md)）。
长 elif 链在嵌套表示下会让 codegen 递归深度等于 elif 数量。

### 5. `for` 的目标解构

`{% for k, v in m.items() %}` 的目标是 `[k, v]`。
解构目标只允许名字列表，不允许嵌套解构（`{% for (a, b), c in ... %}`）——
报 `{unexpected_token, ...}`。Jinja2 支持嵌套，我们不支持，记入差异清单。

目标名字若命中 `?AI_JINJA_RESERVED`（`loop` `super` `caller` 等）→ **warning**，
不是错误：遮蔽是合法的，只是几乎总是笔误。

### 6. `set` 的左值

`atom()`（普通）或 `{attr, Expr, atom()}`（namespace 赋值）。
后者在 [T47](T47.md) 决定是否支持；parser 层无条件产出，由 compiler 报错。

### 7. 位置

每个节点带其开块语句的 loc。`if` 的每个分支带该 `elif` 的 loc，
这样 `{% elif %}` 里的表达式错误能指对行。

## 验收标准

- [ ] 第一档与第二档全部语句形态各有 AST 断言
- [ ] 八类配对诊断各有用例，且 Loc 指向正确位置
- [ ] `{% extends %}` 不在首位只 warning；同层多余内容 warning
- [ ] `if` 的 elif 链产出扁平列表，10 层 elif 不导致深递归
- [ ] `for` 解构、内联 `if`、`recursive` 三个修饰可任意组合
- [ ] 嵌套解构报错
- [ ] 遮蔽 `loop` 等保留名产生 warning 而非错误
- [ ] 第三档语句报 `{unknown_statement, ...}`，文案指向文档
- [ ] fixture 中 `if` / `for` / `set` / `inherit` / `macro` / `include` 组的 AST 层用例点亮
- [ ] `parse/2` 的签名与 `ai_mustache_parser:parse/2` 同形（可作 behaviour 实现）
