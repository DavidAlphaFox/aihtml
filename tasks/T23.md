# T23 · 形态 a：扩展点注册（-mustache_tag）

- **阶段**：5
- **依赖**：[T22](T22.md)、[T13](T13.md)
- **状态**：已完成

## 目标

在 parse_transform 的 pass 1 中实现 `-mustache_tag` attribute 的收集与编译期校验：确认目标模块确实是合法的 `ai_mustache_ext` 实现、marker 未与内置或其它扩展冲突，把配置错误从运行期提前到编译期。

## 交付物

- `ai_mustache_transform` 的 `collect/2` 中 `-mustache_tag` 分支
- `ai_mustache_transform` 的 `expand/2` 中剔除已消费 `-mustache_tag` attribute 的分支
- `format_error/1` 中扩展相关 Reason 的文案（与 [T21](T21.md) 的 `ai_mustache_ext_reg` 共用）
- `test/fixtures/exts/` 下的正例与反例模块（含故意写错的扩展模块）
- `test/ai_mustache_transform_tests.erl` 中形态 a 的用例
- README 中「声明 vs 装配」一节

## 实现要点

### 1. attribute 形态

[06 §1](../designs/06-parse-transform.md) 给出的写法：

```erlang
-mustache_tag({$@, {my_i18n, compile_at}}).
```

需要支持的形态与校验：

| 写法 | 语义 |
|---|---|
| `-mustache_tag({$@, my_i18n}).` | marker `$@` 由 `my_i18n` 接管，callback 用默认的 `compile_tag/4` |
| `-mustache_tag({$@, {my_i18n, compile_at}}).` | 指定自定义 callback 函数名（arity 仍为 4） |
| `-mustache_tag(my_i18n).` | 接管 `my_i18n:markers()` 返回的**全部** marker |
| 其它形态 | 报 `{bad_mustache_tag, Term}` |

第三种形态是推荐写法（marker 集合的唯一真相在扩展模块自己的 `markers/0`，attribute 里重复一遍就有失配风险），要在 README 里主推它；前两种保留，因为它们能表达「本模块只启用该扩展的部分 marker」。

一个模块可以有多条 `-mustache_tag`，全部累积到 `#st.ext_tags`。

### 2. 校验清单

[06 §2.3](../designs/06-parse-transform.md) 明确 parse_transform 在这里的职责是**声明与校验**：

> 编译期检查目标模块确实 `-behaviour(ai_mustache_ext)` 且 `markers/0` 包含该字符，不匹配则报编译错误。

具体逐条：

1. **模块可加载** —— `code:ensure_loaded(Mod)`，失败报 `{ext_module_not_found, Mod}`。注意扩展模块可能与当前模块在同一次 `rebar3 compile` 中编译，编译顺序不确定，可能此时还没有 beam。处置：
   - 先试 `code:ensure_loaded/1`；
   - 失败时降级为**在编译选项 `i` / `outdir` / code path 中查找同名 `.erl` 源文件并静态解析**其 `-behaviour` 与 `markers/0` 的字面量返回值（`markers() -> [$@].` 是常量子句，静态可读）；
   - 两条路都不通时报 `{ext_module_not_found, Mod}`，文案中提示「若扩展模块在同一 app 中，请把它放进独立的 app 或用 `{erl_first_files, ...}` 保证先编译」。这个坑必须在错误文案里说清，否则用户会以为是拼写错。
2. **声明了 behaviour** —— attributes 中含 `{behaviour, [ai_mustache_ext]}` 或 `{behavior, ...}`（两种拼写都要认）。缺失报 `{not_an_ext_module, Mod}`。
3. **导出了 callback** —— `markers/0` 与指定的 `compile_tag/4`（或自定义名/4）在 `module_info(exports)` 中。缺失报 `{ext_missing_callback, Mod, {F, A}}`。
4. **marker 被该模块接管** —— attribute 里写的 marker 必须在 `Mod:markers()` 中。不在则报 `{marker_not_declared, Marker, Mod}`，文案列出 `Mod:markers()` 的实际返回值。
5. **marker 非内置保留字符** —— 内置集合是 `# ^ / > ! = & { } + - *` 共 11 个（[06 §2.4](../designs/06-parse-transform.md)）。冲突报 `{marker_reserved, Marker}`。这个集合的唯一定义在 [T21](T21.md) 的 `ai_mustache_ext:builtin_markers/0`，transform 侧**必须引用它而不是重抄一份**，否则将来加内置 tag 时两处会失配。
6. **同一模块内两条 `-mustache_tag` 注册同一 marker 且指向不同扩展模块** —— 报 `{marker_conflict, Marker, [ModA, ModB]}`，列出全部冲突模块。
7. **marker 字符本身合法** —— 不能是空白、`{`、`}`、非 ASCII 可打印字符（scanner 无法可靠切分），报 `{invalid_marker, Marker}`。

所有校验失败都累积到 `#st.errors`，一次编译报全（[T22](T22.md) §3）。

### 3. 作用域约束 —— 这是形态 a 的核心限制

[06 §2.3](../designs/06-parse-transform.md)：

> **parse_transform 的作用域是单个模块的编译。** `my_i18n` 里的 `-mustache_tag` 声明，`view_index.erl` 编译时**看不见**。

因此本任务实现的**只是校验，不是装配**：

| 机制 | 职责 |
|---|---|
| `-mustache_tag` + parse_transform（本任务） | **声明与校验** |
| `{mustache_opts, [{extensions, [my_i18n]}]}`（[T16](T16.md) / [T21](T21.md)） | **实际装配** |

必须做的配套工作：

- `-mustache_tag` attribute 在 pass 2 中被**剔除**（已消费），不留在最终 forms 里。理由：留着会污染 `module_info(attributes)`，而且它对运行期毫无意义。
- README 中必须有明确一段讲清「只写 attribute 不会生效，还要在 `mustache_opts` 里配 `extensions`」。[06 §2.3](../designs/06-parse-transform.md) 原文：「这一点必须在 README 里讲清楚，否则用户会误以为只写 attribute 就能生效。」
- **可选增强（推荐实现）**：当模块同时有 `-mustache_tag` 与 `-mustache_template`（形态 c，[T25](T25.md)）时，形态 c 的模板编译发生在本模块内，此时 transform **可以**把 `#st.ext_tags` 构建成分派表直接传给 `ai_mustache_compiler:forms/2` 的 `extensions` 选项 —— 这是唯一一个 `-mustache_tag` 能真正参与装配的场景。同理适用于形态 b 的内联模板（[T24](T24.md)）。要在实现与文档中把这个例外说清：**`-mustache_tag` 对本模块内的形态 b/c 生效；对 plugin 编译的 `.mustache` 文件不生效。**
- **一致性警告（推荐实现）**：当 transform 能从 `#st.opts` 读到 `{mustache_opts, [{extensions, Exts}]}` 时，检查 `-mustache_tag` 声明的模块是否都在 `Exts` 里；不在则发 warning `{ext_not_assembled, Mod}`，提示补配置。这条 warning 正是「把配置错误从运行期提前到编译期」的最大价值所在，不要省掉。

### 4. 与 `ai_mustache_ext_reg` 的复用

[T21](T21.md) 已实现装配侧的 `registry/1` 与全部校验函数。本任务**直接复用**这些函数，只做形态转换（attribute term → 模块列表 / marker 白名单）与诊断包装。这样保证：

- parse_transform 编译期报的错，与 plugin 装配时报的错，**文案完全一致**；
- 内置 marker 集合、合法字符集合等规则只有一处定义。

若 `ai_mustache_ext_reg` 的接口不足以支持「只启用某个模块的部分 marker」（形态 1 与 2），在本任务中给它补一个 `registry(Specs)` 重载，而不是在 transform 里另写一套。

### 5. 反例 fixture

[07 阶段 5 验收](../designs/07-roadmap.md) 要求「故意写错的扩展模块能在编译期报出可读错误」。fixture 至少覆盖：

- `bad_ext_no_behaviour.erl` —— 有 `markers/0` 但无 `-behaviour`
- `bad_ext_missing_cb.erl` —— 有 `-behaviour` 但未导出 `compile_tag/4`
- `bad_ext_reserved.erl` —— `markers() -> [$#].`
- `bad_ext_conflict_a.erl` / `bad_ext_conflict_b.erl` —— 都注册 `$@`
- `bad_ext_undeclared.erl` —— attribute 写 `$%` 但 `markers() -> [$@].`
- `bad_ext_invalid_char.erl` —— `markers() -> [${].`

每个 fixture 用 `compile:file/2` 在测试中编译，断言返回的 `{error, Es, Ws}` 中包含预期的 Reason，且 `format_error/1` 的输出包含关键词（模块名、marker 字符、修改建议）。

## 验收标准

- [ ] `-mustache_tag(my_i18n).` / `-mustache_tag({$@, my_i18n}).` / `-mustache_tag({$@, {my_i18n, compile_at}}).` 三种形态都被正确解析
- [ ] 其它形态报 `{bad_mustache_tag, Term}` 并给出正确写法示例
- [ ] 扩展模块不存在时报错，文案提示编译顺序问题与 `erl_first_files` 的处置办法
- [ ] 扩展模块与当前模块在同一次编译中（尚无 beam）时，能通过静态解析 `.erl` 完成校验
- [ ] 未声明 `-behaviour(ai_mustache_ext)`（`behavior` 拼写也认）时报 `not_an_ext_module`
- [ ] 未导出 `markers/0` 或 `compile_tag/4` 时报 `ext_missing_callback` 并指出缺哪个函数
- [ ] attribute 中的 marker 不在 `Mod:markers()` 中时报错，文案列出实际的 `markers()` 返回值
- [ ] 注册内置 marker（`# ^ / > ! = & { } + - *` 任一）时报 `marker_reserved`
- [ ] 同一模块内两条 `-mustache_tag` 注册同一 marker 指向不同模块时报 `marker_conflict` 并列出全部模块
- [ ] 非法 marker 字符（空白 / `{` / `}` / 非 ASCII）报 `invalid_marker`
- [ ] 内置 marker 集合来自 `ai_mustache_ext:builtin_markers/0` 的单一定义，transform 侧无重复硬编码
- [ ] `-mustache_tag` 在生成的 beam 的 `module_info(attributes)` 中**不存在**（已被消费剔除）
- [ ] `-mustache_tag` 声明的模块未出现在 `mustache_opts` 的 `extensions` 中时发出 `ext_not_assembled` warning
- [ ] 同模块内的形态 b/c 能用上 `-mustache_tag` 声明的扩展；plugin 编译的 `.mustache` 不受其影响（有对照测试）
- [ ] 6 个反例 fixture 各有一条测试，断言 Reason 与 `format_error/1` 输出
- [ ] README 有「声明 vs 装配」一节，明确说明只写 attribute 不会对 `.mustache` 文件生效
