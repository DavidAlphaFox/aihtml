## 实现要点

### 1. `docs/jinja.md`

必含四节：

1. **支持范围** —— [09 §4](../designs/09-jinja-syntax.md) 的三档清单，
   明确写出第三档「不做」及其理由。
2. **差异清单** —— [10 §9](../designs/10-jinja-semantics.md) 的 J1–J13，
   逐条给出示例与「你应该怎么写」。**每条都要有对应的 fixture 编号**，
   读者能自己去 `test/jinja_spec/` 里查证。
3. **配置项** —— `jinja_opts` 全部键、默认值、是否进 stamp。
4. **内置 filter / test 清单** —— 含每个的 `@safe` 分类。

### 2. README 的双引擎一节

放 [10 §10](../designs/10-jinja-semantics.md) 的对照表。
**最重要的一条是真值差异**：`0` 在 mustache 里是真、在 Jinja 里是假。
同一个仓库里两套语义，这是最容易出事故的地方，要放在显眼位置。

### 3. 示例

`examples/views/jinja/` 至少覆盖：继承（base + 两级子模板）、宏、
import、include、filter 链、`for` + `loop`。
`examples/rebar.config` 加 `jinja_opts` 与第二个 hook。

`examples/run.sh` 跑通两个引擎。

### 4. 性能基线

`bench/` 增加 Jinja 侧。要测的三项：

- 静态模板（验证 literal pool 折叠）
- 简单插值 + filter 链
- 继承 + block 覆盖（验证 `maps:merge` 的开销确实可忽略）

与 mustache 侧同规格对比，结论写进 `bench/README.md`。
**如果继承的 merge 开销不可忽略，要在这里发现并回头优化**，而不是发布后。
