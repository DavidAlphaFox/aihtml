# T19 · rebar3 mustache migrate 子命令

- **阶段**：4
- **依赖**：[T08](T08.md)
- **状态**：已完成

## 目标

实现 `rebar3 mustache migrate` provider：把 v0.3.x 的「扁平 context + 全路径寻址」模板机械改写为标准 mustache 的 context stack 写法，默认只输出 diff，`--write` 才落盘，无法确定的改写原样保留并在报告中列出。

## 交付物

- `rebar3_aihtml/src/rebar3_aihtml_migrate.erl` —— migrate provider（`init/1` · `do/1` · `format_error/1`）
- `rebar3_aihtml/src/rebar3_aihtml_rewrite.erl` —— 基于 AST 的前缀剥离算法与源文本重写
- `rebar3_aihtml/src/rebar3_aihtml_diff.erl` —— 统一 diff 格式输出

## 实现要点

### 1. Provider 注册

migrate 是 `mustache` 的子命令（[05 §5](../designs/05-rebar3-plugin.md)），走 rebar3 的 namespace 机制：

```erlang
init(State) ->
    P = providers:create([
          {name,       migrate},
          {module,     ?MODULE},
          {namespace,  mustache},
          {bare,       true},
          {deps,       [app_discovery]},
          {example,    "rebar3 mustache migrate"},
          {opts,       [{write,   $w, "write",   boolean, "把改写结果落盘（默认只输出 diff）"},
                        {verbose, $v, "verbose", boolean, "输出每处改写的详细说明"}]},
          {short_desc, "Migrate v0.3.x flat-context templates to standard mustache semantics"},
          {desc,       "..."}]),
    {ok, rebar_state:add_provider(State, P)}.
```

注意 `{namespace, mustache}` 与 [T16](T16.md) 中 compile provider 的 `{namespace, default}, {name, mustache}` 是两套东西：前者使 `rebar3 mustache migrate` 可用，后者使 `rebar3 mustache` 可用。rebar3 允许这种组合（bare provider 名与 namespace 名同名），但要在 [T20](T20.md) 中实测确认 `rebar3 mustache` 与 `rebar3 mustache migrate` 都能正确分派，不存在歧义。若实测有歧义，退路是把 migrate 挂在 default namespace 下并命名为 `mustache_migrate`，同时在 desc 中说明。

### 2. 改写规则

[03 §7.1](../designs/03-semantics.md) 给出的核心规则：

> **在 section `{{#X}}` 的 body 内部，把以 `X.` 开头的引用剥掉这层前缀。**

```diff
- {{#user}}{{user.name}}{{/user}}
+ {{#user}}{{name}}{{/user}}

- {{# items}}{{+ items.current}}<li>{{items.name}}</li>{{/ items.current}}{{/ items}}
+ {{# items}}{{+ current}}<li>{{name}}</li>{{/ items.current}}{{/ items}}
```

算法（[03 §7.2](../designs/03-semantics.md)）：

1. 用 [T08](T08.md) 的 parser 解析模板得到带 `loc()` 的 AST（[04 §1](../designs/04-codegen.md)）。**必须用 AST 而不是正则**：正则会错改注释 `{{! items.x }}`、字符串里的花括号、自定义分隔符段落。
2. 深度优先遍历，维护一个「作用域前缀栈」`Scopes :: [keys()]`。进入 `{section, _, Keys, Body}` 时压入 `Keys`；`{inverted, ...}` / `{has, ...}` 不改变作用域（[03 §2](../designs/03-semantics.md) 明确 `{{^}}` 与 `{{+}}` 不压栈），因此**不压入**。
3. 对每个 `{var, Loc, Keys, _}` / `{section, Loc, Keys, _}` / `{has, Loc, Keys, _, _}` / `{lambda, Loc, Keys}` 节点，检查 `Keys` 是否以栈顶作用域的 `Keys` 为前缀。是则剥掉这层前缀，产出一条 `#edit{loc, old_keys, new_keys}`。
4. 只剥**一层**（栈顶那层），不递归向外层剥。多层嵌套时，由于遍历是自外向内、每层各自匹配，效果自然是逐层剥掉的。
5. `{{/X}}` 闭合标签必须与被改写的 `{{#X}}` 保持一致 —— 改 section key 时开闭两处都要改。注意上面第二个例子中 `{{/ items.current}}` 也应同步改为 `{{/ current}}`（设计文档的 diff 示例这里未同步，实现时以「开闭必须一致」为准）。

### 3. 源文本重写（保留原貌）

**不能用「AST → 重新序列化」的方式生成新模板** —— 那会丢掉注释、空白、自定义分隔符、原有的 `{{# items}}` 中的空格风格。必须做**基于位置的原地文本替换**：

- AST 节点的 `loc()` 是 `{Line, Col}`。要做原地替换，需要能定位到 tag 的**字节区间**。若 parser 只给 `{Line, Col}`，本任务需要在 [T08](T08.md) 的 AST 上补一个可选的 `span` 字段，或由 migrate 自己从 `{Line, Col}` 出发在源文本中重新定位 tag 的起止（从该位置开始匹配当前生效的 open delimiter，扫到对应 close delimiter）。**推荐前者**：在 parser 阶段就记录 `{StartOffset, Len}`，migrate 侧的实现会简单且不易错，同时对自定义分隔符天然正确。如果 [T08](T08.md) 未提供，在本任务中向 parser 提交这个增补，并在 AST 定义中标注该字段仅 migrate 使用。
- 替换只动 tag 内部的 key 文本，不动 delimiter、不动 tag 内的空白风格（`{{ items.name }}` → `{{ name }}`，保留两侧空格）。
- 所有编辑按 offset **降序**应用，避免前面的替换让后面的 offset 失效。

### 4. 无法确定的情形 —— 原样保留并报告

[03 §7.2](../designs/03-semantics.md) 明确「不做的事」：

> 无法确定的（比如引用了兄弟 section 的变量、跨 partial 的隐式依赖）原样保留并在报告中列出，交人工处理。

必须识别并列入报告的情形：

| 情形 | 例子 | 处置 |
|---|---|---|
| 引用了兄弟 section 的键 | `{{#a}}{{b.x}}{{/a}}`，`b` 是同级另一个 section | 不改，报告 |
| 引用了外层但非直接父级的前缀 | `{{#a}}{{#b}}{{a.x}}{{/b}}{{/a}}` | 不改，报告（新语义下栈回溯可能仍能找到，但也可能被内层同名键遮蔽） |
| partial 内部的引用 | `{{> shared/item}}` 的被调模板 | 不改，报告：partial 以调用点的栈渲染，改写需要跨文件推导 |
| section key 本身含点 | `{{#a.b}}...{{/a.b}}` | 不改，报告：新语义下 `a.b` 的下钻不回溯，语义可能变化 |
| lambda `{{*f}}` 的参数 | —— | 不改，报告：[03 §5](../designs/03-semantics.md) 指出 lambda 收到的从全局 Ctx 变成栈顶 frame，需人工检查 |
| 自定义分隔符段落内 | `{{=<% %>=}}` 之后 | 正常处理（parser 已消化），但在 verbose 报告中标注 |

报告格式（打到 stdout，不写文件）：

```
views/complex.mustache
  rewritten: 4
  manual review needed:
    line 12: {{b.x}} inside {{#a}} -- references a sibling section
    line 20: {{*yield}} -- lambda now receives the top frame, not the root context (see designs/03 §5)
```

结尾打一条全局汇总：`N files, M rewrites, K items need manual review`。K 大于 0 时 `do/1` 仍返回 `{ok, State}`（migrate 是辅助工具，不该因为有人工项而失败），但退出信息要醒目。

### 5. diff 输出与 `--write`

- 默认（无 `--write`）：对每个有改动的文件输出统一 diff 格式（`--- a/views/x.mustache` / `+++ b/views/x.mustache` / `@@ -L,C +L,C @@`）。自己实现一个最小 unified diff（按行做最长公共子序列），**不调用外部 `diff` 命令**（跨平台、零依赖）。改动量小，可以只输出改动行及前后各 3 行上下文。
- `--write`：原子化写盘（写 `.tmp` 再 `rename`，与 [T17](T17.md) §4 一致）。**不做备份文件** —— 模板在 git 里，`.orig` 只会制造垃圾；但在写盘前检查 `git status` 是不现实的，改为在 `--write` 时先打一条 warning 提示「确保工作区已提交」。
- migrate **绝不修改** `out_dir` 下的生成物，只动 `views_dir` 下的源模板。
- 扫描范围与 [T17](T17.md) §2 完全一致（复用 `rebar3_aihtml_scan`），保证 migrate 与 compile 看到的是同一批文件。

### 6. 幂等性

migrate 必须幂等：对已迁移过的模板再跑一次应产出零改动。这是可测的性质，也是算法正确性的强约束 —— 剥完前缀后，`{{name}}` 不再以 `items.` 开头，第二遍自然不匹配。测试中必须有「跑两遍」的 case。

## 验收标准

- [ ] `rebar3 mustache migrate` 与 `rebar3 mustache` 都能正确分派，互不干扰
- [ ] `{{#user}}{{user.name}}{{/user}}` 被改写为 `{{#user}}{{name}}{{/user}}`
- [ ] `{{# items}}{{+ items.current}}<li>{{items.name}}</li>{{/ items.current}}{{/ items}}` 中三处 `items.` 前缀都被剥掉，且 `{{/ items.current}}` 与其开标签同步改写
- [ ] tag 内的空白风格被保留：`{{ items.name }}` → `{{ name }}`
- [ ] 注释 `{{! items.x }}` 与自定义分隔符段落不被误改
- [ ] `{{^x}}` 与 `{{+x}}` 的 body 内不发生前缀剥离（它们不压栈）
- [ ] 引用兄弟 section 的键、partial、含点的 section key、lambda 都被原样保留并列入人工复查报告
- [ ] 默认只输出 diff，`views/` 下文件字节不变；`--write` 后文件按 diff 改写
- [ ] 对已迁移的模板重跑产出零改动（幂等）
- [ ] 本仓 `examples/shared/{item,user,level}.mustache` 与 `examples/complex.mustache` 跑 migrate 的结果与 [03 §7.3](../designs/03-semantics.md) 的预期一致
