# 12 · 工具链：plugin 参数化与 parse_transform

前置阅读：[05](05-rebar3-plugin.md)、[06](06-parse-transform.md)。
本文只写**变更**，不重复既有设计。

## 1. plugin：从「mustache 专用」到「引擎参数化」

### 1.1 改动范围

`rebar3_aihtml` 的九个模块里，八个只需把「写死的 mustache」换成「从 `#mopts{}` 取 engine」：

| 模块 | 改动 |
|---|---|
| `rebar3_aihtml_opts` | `#mopts{}` 增加 `engine` 字段；`raw/2` 读的配置键从 `mustache_opts` 变成参数 |
| `rebar3_aihtml_scan` | `ai_mustache_compiler:source_hash/2` → `Engine:source_hash/2`；`absorb/4` 匹配的 attribute 名从 `mustache_source` 变成 `Engine:attribute()` |
| `rebar3_aihtml_name` | `ai_mustache_ast:module_name/2` → `Engine:module_name/2` |
| `rebar3_aihtml_emit` | `ai_mustache_parser:parse/2` → `Engine:parse/2`；`ai_mustache_compiler:forms/2` → `Engine:forms/2`；banner 文案参数化 |
| `rebar3_aihtml_check` | 无引擎相关逻辑，只需接受 engine 以便错误文案正确 |
| `rebar3_aihtml_gc` | banner 前缀参数化（孤儿识别靠它） |
| `rebar3_aihtml_stale` | 属性名参数化 |
| `rebar3_aihtml_prv` | 抽出 `run/3`（多一个 engine 参数），provider 定义保持 |
| `rebar3_aihtml_migrate` | **不动**。migrate 是 mustache 语义迁移专用，Jinja 没有对应需求 |

**新增**一个模块 `rebar3_aihtml_jinja`，只做 provider 注册，`do/1` 转发给
`rebar3_aihtml_prv:run/3` 并传 `ai_jinja_engine`。

### 1.2 `#mopts{}` 的变化

```erlang
-record(mopts, {engine :: module(),        %% 新增：ai_mustache_engine | ai_jinja_engine
                app_name, app_dir, ebin_dir, src_dirs,
                views_dir, views_rel, out_dir, out_rel,
                suffix, prefix, extensions, ext_opts, line_map, wae,
                engine_opts :: map(),      %% 原 compiler_opts，改名以示中立
                compiler_opts}).
```

`engine_opts` 里 Jinja 独有的键：`escape` · `trim_blocks` · `lstrip_blocks` ·
`keep_trailing_newline` · `strict_undefined`。它们**全部进 stamp**（改了要重编），
与 mustache 侧 `normalize_opts/1` 的处理方式一致。

### 1.3 配置

```erlang
{plugins, [rebar3_aihtml]}.
{provider_hooks, [{pre, [{compile, mustache}, {compile, jinja}]}]}.

{jinja_opts, [{views,   "views"},
              {suffix,  ".j2"},
              {out_dir, "_gen"},
              {prefix,  "j2_"},
              {escape,  true},
              {trim_blocks, true},
              {lstrip_blocks, true},
              {extensions, [my_filters]},
              {line_map, true}]}.
```

`?R3A_KNOWN_KEYS` 拆成两张表：`?R3A_MUSTACHE_KEYS` 与 `?R3A_JINJA_KEYS`。
未知键的警告文案要指出是哪个引擎的配置，否则用户在 `jinja_opts` 里写了
mustache 才有的键时会看到一条不知所云的提示。

### 1.4 两个引擎共用 out_dir

默认都是 `_gen`。前缀不同（`view_` vs `j2_`）保证不撞名。

**孤儿清理必须区分引擎**：`rebar3_aihtml_gc` 靠 banner 首行识别「这是我们生成的」，
现在要进一步识别「这是哪个引擎生成的」，否则 `rebar3 jinja` 会把
`rebar3 mustache` 刚生成的文件当孤儿删掉——而且因为两个 provider 都挂在 `pre compile` 上，
这会变成一个每次构建都发生、且顺序相关的诡异 bug。

banner 改为：

```
%% Generated by rebar3_aihtml (jinja) from views/page.j2 -- DO NOT EDIT.
```

gc 只回收 banner 中引擎标记与自己相同的文件。**这一条要有专门的回归测试**：
同一个 out_dir 下放两个引擎的产物，跑两次 `rebar3 compile`，文件数不得变化。

### 1.5 全项目重名检测

`rebar3_aihtml_check` 的模块名冲突检测本就在全项目范围做。两个引擎的产物
要进入**同一张表**，因此 provider 不能各查各的。做法：把冲突表存进 `rebar_state`
（`rebar_state:set(State, {aihtml, modules}, Table)`），第二个 provider 读取并追加。

## 2. parse_transform

`ai_jinja_transform` 与 `ai_mustache_transform` 结构完全一致
（三 pass：collect / expand / inject），只是形态换成 Jinja 的：

| 形态 | mustache | Jinja |
|---|---|---|
| (a) 扩展声明 | `-mustache_tag(Mod)` | `-jinja_ext(Mod)`（filter/test 注册） |
| (b) 内联模板 | `ai_mustache:inline(~"...", Ctx)` | `ai_jinja:inline(~"...", Ctx)` |
| (c) 文件模板 | `-mustache_template({Name, Path})` | `-jinja_template({Name, Path})` |

三条落地要求：

1. **`-jinja_ext` 的校验在编译期做**：读 `Mod:filters/0` 与 `Mod:tests/0`，
   与内置表比对，冲突即报错。与 mustache 的 marker 冲突检测（[06](06-parse-transform.md)、
   `ai_mustache_ext_reg`）是同一个套路，可复用其静态扫描 `.erl` 的手法
   （模块尚未编译时也要能校验）。
2. **形态 (b) 的运行期回退必须与展开路径行为一致**。mustache 侧的经验
   （`ai_mustache:inline/2` 对 partial 的处理）在这里放大了：Jinja 的内联模板
   拒绝 include/extends/import/block（[11 §8](11-jinja-codegen.md)），
   **运行期回退路径必须拒绝同样的东西**，否则同一份模板加不加 parse_transform
   会一个报错一个静默渲染成空。
3. **形态 (c) 的 rebar3 依赖追踪**沿用 `ai_html_path:scan/1`——
   plugin 扫描 `.erl` 找 `-jinja_template`，模板 hash 变了就 touch 该 `.erl`。
   属性名作为参数传入，两个引擎共用一份实现。

### 2.1 一个模块里混用两个引擎

合法且必须支持：

```erlang
-compile({parse_transform, ai_mustache_transform}).
-compile({parse_transform, ai_jinja_transform}).

-mustache_template({legacy, "views/legacy.mustache"}).
-jinja_template({page, "views/page.j2"}).
```

两个 transform 互不认识对方的 attribute，各自只消费自己的。
唯一要求：**都不能假设自己是第一个或最后一个 transform**——
这条 `ai_mustache_transform` 已经满足（`module_of/1` 遍历查找而非取 `hd/1`），
`ai_jinja_transform` 照抄即可。

## 3. `ai_jinja_dev`

与 `ai_mustache_dev` 一一对应：读生成模块的 `-jinja_source` attribute，
用 `ai_jinja_compiler:source_hash/2` 重算 stamp 比对，变了就重编重载。

**两个 dev 模块不合并。** 它们各自只有约 200 行，且要读不同的 attribute、
调不同的 compiler；合并出的公共模块需要接受一个 engine 参数，
调用方（用户在开发期请求入口手写的一行 `ai_mustache_dev:reload(all)`）
反而要多写一个参数。

新增一个便利函数 `ai_html_dev:reload_all()`，同时刷新两个引擎，仅此而已。

## 5. 自定义 tag（不在 v1）

mustache 的扩展点是 `{{@ key}}` 这种自定义 marker，扩展模块提供 `compile_tag/4`
返回 abstract expression。Jinja 的对应物是自定义 `{% mytag %}` 语句。

v1 **不做**。理由：Jinja 的语句有块结构、有参数表达式、有作用域影响，
扩展接口要暴露的东西远比 mustache 的 marker 多；在还没有真实需求驱动的情况下
设计这个接口，几乎注定要推翻重来。

v1 提供的扩展点只有 filter 与 test（[10 §8.4](10-jinja-semantics.md)），
这两者接口极窄（一个普通函数），且覆盖绝大多数「我要加点自己的东西」的需求。
